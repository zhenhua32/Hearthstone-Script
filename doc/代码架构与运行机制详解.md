## 2. 一句话理解项目

这是一个以 Windows 桌面自动化为边界、以游戏日志为输入、以 WAR 战斗模型为中间状态、以插件策略为决策层、以 JNA/DLL 鼠标和进程控制为执行层的炉石传说脚本。

核心不是“定时点击几个坐标”，而是下面这条闭环：

~~~text
游戏进程 / 日志
    ↓
LoadingScreen.log、Decks.log、Power.log
    ↓
日志监听器与 PowerLogUtil
    ↓
WAR / WarEx / Mode / 当前阶段
    ↓
DeckStrategyActuator
    ↓
CardAction、DeckStrategy、MCTS 或权重组合策略
    ↓
模拟验证 + 鼠标/原生 DLL 执行
    ↓
游戏状态变化，再次写入日志
~~~

从架构层次看，可以分成四层：

~~~mermaid
flowchart LR
    UI["JavaFX UI / FXML"] --> APP["hs-script-app<br/>Core、状态、模式、日志"]
    APP --> SDK["card-sdk / strategy-sdk / plugin-sdk"]
    SDK --> PLUGINS["基础插件 / 外部插件 / 用户策略"]
    APP --> WIN["JNA 与 DLL<br/>窗口、进程、鼠标、注入、日志读取"]
    GAME["炉石与战网进程"] --> LOG["LoadingScreen.log<br/>Decks.log<br/>Power.log"]
    LOG --> APP
    PLUGINS --> EXEC["CardAction / Strategy<br/>模拟与真实执行"]
    EXEC --> WIN
    WIN --> GAME
~~~

## 4. 构建、运行模式与运行目录

### 4.1 Maven 构建

hs-script-app 有两个 Maven profile：

| Profile | run.mode | 产物方式 | 说明 |
|---|---|---|---|
| jvm | jar | Maven Assembly 打包 | 默认 profile，依赖 JRE/JDK，插件体系完整 |
| native | native | GraalVM Native Image | 使用 native-maven-plugin，入口是 MainKt，生成 Windows 原生程序 |

根目录提供 mvnw 与 mvnw.cmd。通常从根目录构建聚合工程；Native 构建还要求本机具备相应 GraalVM/native-image 工具链。README 明确说明 Native 版本不支持 JVM 插件，因此插件开发和插件调试应优先使用 JVM 版本。

### 4.2 根目录路径约定

hs-script-app 的 PathConst.kt 以 System.getProperty("user.dir") 作为 ROOT_PATH。因此运行目录不是一个无关细节，而是配置、数据库、DLL、日志和插件的解析基准。

| 路径 | 作用 |
|---|---|
| config/script.ini | ini 配置文件；首次读取时自动创建并补齐 ConfigEnum 中的键 |
| log/ | 脚本自身的日志输出目录（由 logback 配置决定） |
| plugin/ | 外部 JVM 插件目录 |
| data/cardgroup/ | 卡组权重/卡牌组文件目录，扩展名为 .cardgroup |
| statistics.db | 统计数据 SQLite 数据库 |
| hs_cards.db | 卡牌基础数据库，根仓库已包含 |
| lib/ | JNA/native DLL、注入工具和运行库 |
| lib/dll/ | CSystemDll、日志读取、通知等 DLL 的解析位置 |
| aot/ | AOT 缓存文件目录 |
| new_version_temp | 更新下载临时文件 |

游戏目录下重点使用：

~~~text
<炉石安装目录>/Logs/Power.log
<炉石安装目录>/Logs/LoadingScreen.log
<炉石安装目录>/Logs/Decks.log
<炉石安装目录>/log.config
<炉石安装目录>/client.config
~~~

### 4.3 运行时原生文件

代码通过 ResourceFile 常量和 SystemUtil 查找下列资源：

inject-util.exe、install-drive.exe、card-update-util.exe、update.exe、hs.dll、hs_base.dll、bn.dll、capture_reader.dll、log_reader.dll 和 unlock.bat。

其中：

- CSystemDll 负责窗口、鼠标、进程、驱动、托盘、捕获、注入相关控制。
- LogReader 加载 log_reader.dll，把游戏日志暴露成可按通道读取的内存流。
- Main.kt 设置 jna.library.path=lib，让 JNA 能够解析 lib/dll 下的库。

## 5. 程序启动与关闭流程

### 5.1 入口：Main.kt

MainKt.main(args) 按以下顺序执行：

1. 设置 JNA 搜索路径为 lib。
2. 根据 --aot 标记设置 ScriptStatus.aotMode。
3. 创建 Windows 命名互斥体 hs-script.lock，防止重复启动。
4. 如果发现已有实例，调用 WindowUtil.hideLaunchPage() 后结束当前进程。
5. 重新配置 logback 文件级别过滤器。
6. 保存命令行参数到 ScriptStatus.programArgs。
7. 启动 JavaFX MainApplication。

### 5.2 MainApplication 的初始化顺序

MainApplication.start 先处理 --window 参数；普通启动则执行：

~~~text
preInit
  ├── CardAction.commonActionFactory = DEFAULT.createNewInstance
  ├── Platform.setImplicitExit(false)
  ├── launchService
  │     ├── TaskManager
  │     ├── Core
  │     ├── GlobalHotkeyListener
  │     ├── VersionListener
  │     ├── WorkTimeListener
  │     └── StatisticsListener
  ├── CardGroupUtil.applyEnabledCardGroups
  └── 注册 ShutdownHook

InitializerConfig.initializer.init()
  ├── BaseInitializer
  ├── GamePathInitializer
  ├── GameLogInitializer
  ├── PluginInitializer
  ├── DriverInitializer
  └── ServiceInitializer

showMainPage
  └── afterShowing
        ├── 创建原生托盘
        ├── 检查管理员权限和系统环境
        ├── 处理 --pause / --aot 参数
        ├── 应用软件目录保护模式
        └── 隐藏启动页
~~~

--page=<WindowEnum> 可以直接打开指定页面；--pause=false 会在页面显示后自动解除暂停。首次运行和版本变化时会打开 About/版本说明页面。

### 5.3 关闭流程

ShutdownHookConfig 注册的 shutdown hook 会按顺序完成：

- 如果只保护运行期间，则解除程序目录保护。
- 移除系统托盘。
- 保存窗口和设置布局。
- 按配置卸载 DLL/驱动。
- 关闭捕获、鼠标范围限制、鼠标轨迹、鼠标 hook、反作弊 hook。

因此退出时不应只结束 JavaFX 窗口；程序设计上需要走正常退出路径，以便恢复原生状态。

## 6. 核心状态机

### 6.1 暂停状态：PauseStatus

PauseStatus.isPause 初始值为 true，是一个 JavaFX 可监听属性。

- 设为 true：Core 将 WorkTimeListener.working 置为 false，重置 Mode，停止任务并保留主界面。
- 设为 false：检查工作时间，允许时启动 Core.start()；不允许时提示是否睡眠系统。
- asyncSetPause 把状态变更投递到 EXTRA_THREAD_POOL，适合托盘和全局热键调用。

### 6.2 工作时间：WorkTimeListener

工作时间监听器大约每 30 秒检查一次当前工作时间规则，决定：

- 当前是否允许工作；
- 当前使用哪一个卡组策略、运行模式和卡组位置；
- 是否在工作/休息切换时执行配置的 Operate；
- 下一个可用工作时间的提示。

WORK_TIME_RULE_HIGH_PRIORITY 打开后，策略和卡组位置可以由当前工作时间规则覆盖默认设置。

### 6.3 界面模式：Mode

Mode 表示 LoadingScreen 日志中的游戏界面，不等同于战斗阶段。

| 层次 | 代表值 | 作用 |
|---|---|---|
| 界面模式 | STARTUP、LOGIN、HUB、TOURNAMENT、ADVENTURE、GAMEPLAY、FATAL_ERROR 等 | 由 ScreenLogListener 解析并驱动点击/跳转 |
| 运行模式 | STANDARD、WILD、CASUAL、PRACTICE 等 | 由策略声明支持范围，决定匹配或练习入口 |
| 战斗阶段 | FILL_DECK、DRAWN_INIT_CARD、REPLACE_CARD、SPECIAL_EFFECT_TRIGGER、GAME_TURN、GAME_OVER | 由 PowerLogListener 驱动战斗模型 |
| 回合步骤 | BEGIN_MULLIGAN、MAIN_READY、MAIN_ACTION、MAIN_END、FINAL_GAMEOVER 等 | 由 Power.log 的 STEP 标签细化当前阶段 |

Mode.currMode 改变时，会把旧模式和新模式放入队列，异步调用旧模式的 afterLeave() 和新模式的 entering()。nextMode 如果 5 秒内没有等到日志确认，会采用超时兜底，把目标模式当作当前模式。

### 6.4 战斗阶段

hs-script-base 中的 WarPhaseEnum 只有 6 个阶段：

1. FILL_DECK：创建游戏、识别双方、建立牌局。
2. DRAWN_INIT_CARD：初始抽牌和玩家身份确认。
3. REPLACE_CARD：换牌阶段。
4. SPECIAL_EFFECT_TRIGGER：开局特殊效果和准备步骤。
5. GAME_TURN：正常回合，执行出牌、攻击、技能和结束回合。
6. GAME_OVER：结算、统计并清理牌局。

## 7. Core、初始化链与 Starter 责任链

### 7.1 Core

Core.start(force) 使用 CORE_THREAD_POOL 和 ReentrantLock 防止并发启动：

1. 检查暂停和工作时间。
2. 检查炉石安装路径与战网程序路径是否有效。
3. 将 WorkTimeListener.working 设为 true。
4. 调用 StarterConfig.starter.start()。
5. 如果路径无效，则通知用户打开设置，并重新暂停。

Core.restart 会先暂停、停止游戏进程、重置屏幕日志解析状态，再恢复运行。

### 7.2 Initializer 责任链

| 初始化器 | 实际行为 |
|---|---|
| BaseInitializer | 初始化默认卡牌动作工厂；通过反射把 ModeEnum 绑定到 strategy.mode，把 WarPhaseEnum 绑定到 strategy.phase |
| GamePathInitializer | 读取配置；配置为空时尝试从 Windows 注册表推断战网和炉石路径；更新路径有效性 |
| GameLogInitializer | 修改游戏 log.config 的 LoadingScreen、Decks、Power 部分，打开文件打印和详细日志；修改 client.config 日志大小上限 |
| PluginInitializer | 调用 PluginManager.loadAllPlugins() 加载内部和外部插件 |
| DriverInitializer | 在驱动鼠标模式下安装/加载 Interception 驱动；必要时要求管理员权限 |
| ServiceInitializer | 按优先级启动启用的配置服务；服务包括自动开始、代理、鼠标步长、阻止 AC 等 |

### 7.3 Starter 责任链

StarterConfig 用 buildStarter 组装如下链条：

~~~text
TaskManager
  → ClearStarter
  → PrepareStarter
  → PlatformStarter
  → LoginPlatformStarter
  → GameStarter
  → InjectGameStarter
  → InjectedAfterStarter
  → LogListenStarter
  → ExceptionListenStarter
~~~

| Starter | 责任 |
|---|---|
| ClearStarter | 清理上一轮任务、关闭旧日志通道和状态 |
| PrepareStarter | 检查鼠标、策略、日志开关；决定磁盘或内存日志模式 |
| PlatformStarter | 启动/寻找 Battle.net，监控战网窗口 |
| LoginPlatformStarter | 处理登录页面、密码输入和登录按钮 |
| GameStarter | 启动/寻找 Hearthstone、重试、更新窗口句柄和窗口矩形 |
| InjectGameStarter | 根据配置决定是否注入 hs.dll、日志、捕获、反作弊或范围限制能力，并等待连接 |
| InjectedAfterStarter | 在注入成功后启用 hook、捕获、渲染和鼠标范围限制 |
| LogListenStarter | 启动 LoadingScreen.log、Decks.log、Power.log 监听链 |
| ExceptionListenStarter | 检查空闲/异常时间，必要时重新启动脚本链 |

Starter 都继承 AbstractStarter，通过责任链继续下一个节点，并在 TaskManager 中登记可取消任务；暂停时由任务管理器统一关闭。

## 8. 日志输入与解析管线

### 8.1 三类日志

| 日志 | 监听器 | 解析结果 |
|---|---|---|
| LoadingScreen.log | ScreenLogListener | Mode.currMode、Mode.nextMode、游戏退出/销毁事件 |
| Decks.log | DeckLogListener | 当前玩家的牌组 ID、名称、卡组代码 |
| Power.log | PowerLogListener | War、玩家、实体、区域、标签、区块、阶段、回合和战斗结束 |

### 8.2 磁盘模式和内存模式

AbstractLogListener.waitLogCreated() 根据 ScriptStatus.gameLogMode 选择：

- DISK：找到最新游戏日志目录，创建/打开目标日志文件，用 DiskLogFile 通过 UTF-8 文件读取。
- MEMORY：先初始化 LogReader，等待对应通道出现，用 MemoryLogFile 读取 native 日志通道。

日志文件最多等待约 15 秒；暂停会中断等待。监听任务默认在 LISTEN_LOG_THREAD_POOL 上按固定延迟调度，暂停或不在工作时间时停止。

MemoryLogFile 维护通道 ID、读取位置和读写锁，支持按行、按批、读取全部、seek、reset、available 和 skip。底层能力来自 log_reader.dll 的 nativeOpenChannel、nativeReadLine、nativeSetPosition 等 JNI/native 对接方法。

### 8.3 Power.log 的解析

PowerLogUtil 维护两个有界栈：

- blockStack：最多 20 层，用于处理 BLOCK / BLOCK_END。
- fullCardStack：最多 10 层，用于聚合 FULL_ENTITY 和触发发现/时间线选择。

主要处理函数：

| 函数 | 处理内容 |
|---|---|
| dealShowEntity | 解析 SHOW_ENTITY，补充现有卡牌实体信息 |
| dealFullEntity | 创建完整卡牌实体，更新卡牌 ID、区域、玩家、创建者等 |
| dealChangeEntity | 解析 CHANGE_ENTITY，更新实体属性 |
| dealTagChange | 处理资源、费用、攻击、生命、区域、当前玩家等标签变化 |
| dealBlock / dealBlockEnd | 建立和收束动作区块，恢复来源/目标关系 |
| parseCommonEntity | 从 Power.log 行中解析实体的 id、CardID、zone、zonePos、player 等字段 |
| isRelevance | 过滤无关日志，并检测日志超过配置上限的情况 |
| formatLogFile | 在需要分析或续写时复制/整理日志文件 |

发现和时间线使用特殊实体 ID：TIME_000ta 表示保留，TIME_000tb 表示回溯。发现线程会设置 WAR.isChooseCardTime，再由 DeckStrategyActuator.discoverChooseCard 回调策略并点击对应位置。

### 8.4 阶段处理器

| 阶段处理器 | 关键事件 |
|---|---|
| FillDeckPhaseStrategy | CREATE_GAME 时初始化 WarEx，在 TURN=1 后进入初始抽牌 |
| DrawnInitCardPhaseStrategy | 根据玩家 ID、游戏 ID 和硬币等信息识别我方与对手，进入换牌 |
| ReplaceCardPhaseStrategy | 处理 MULLIGAN_STATE=INPUT，调用换牌策略；受胜率、连胜和超时设置约束 |
| SpecialEffectTriggerPhaseStrategy | MAIN_READY 后进入正常游戏回合 |
| GameTurnPhaseStrategy | MAIN_ACTION 时判断是否轮到我方，启动出牌线程；MAIN_END 时取消本回合任务 |
| GameOverPhaseStrategy | 结束战斗、统计结果、清理解析状态并安排下一局 |

## 9. 战斗状态模型：WAR、WarEx 与卡牌对象

### 9.1 WAR 全局单例

hs-script-card-sdk 暴露全局 WAR = War(true)，策略和应用层通过它访问当前牌局。War 在 BaseWar 的基础上增加：

- cardMap: entityId -> Card；
- currentPlayer、firstPlayerGameId、currentPhase、currentTurnStep；
- 我方/对手/双方玩家引用；
- isChooseCardTime、maxEntityId；
- 设置玩家、阶段和步骤的同步日志方法；
- deepClone，供 MCTS 模拟使用；
- 未知战局对象，供缺少真实信息时使用。

### 9.2 玩家和区域

Player 包含以下区域：

handArea、playArea、secretArea、graveyardArea、deckArea、setasideArea、removedfromgameArea、cosmeticArea。

重点容量约束：

- 手牌上限 10。
- 战场上限 7。
- 奥秘区上限 5。
- 牌库模型最多 60。

PlayArea 额外维护英雄、英雄技能、武器、随从和隐藏槽位；添加/移除卡牌时触发战吼、区域变化和战场效果。HandArea.drawCard 在模拟环境中会创建占位未知卡，真实实体则来自日志。

### 9.3 Card 和 BaseCard

BaseCard 是卡牌标签的值模型，覆盖：

- 类型、卡牌 ID、费用、攻击、生命、耐久度、护甲、伤害；
- 嘲讽、圣盾、潜行、冻结、风怒/超级风怒、冲锋/突袭、吸血、剧毒；
- 战吼、亡语、发现、选择一张、可交易、锻造、休眠、地点冷却；
- 控制者、创建者、种族、法术强度、泰坦、星舰组件、发射台；
- 手牌/战场回合计数等隐藏标签。

Card 在 BaseCard 之外维护：

- CardAction；
- 所在 Area；
- 子卡/附着卡；
- 攻击次数、未知状态；
- 受伤回调和卡牌 ID 改变回调。

伤害 setter 会触发受伤监听，并通知我方和对手场上/手牌的 CardAction；injured 会按免疫、圣盾、英雄受伤加成等规则计算实际结果。

### 9.4 动作模型

动作是“可以执行或模拟的副作用”：

| 动作 | 说明 |
|---|---|
| AttackAction | 一个实体攻击另一个实体或英雄 |
| PlayAction | 从手牌打出卡牌、交易、施放法术或触发卡牌逻辑 |
| PowerAction | 使用英雄技能 |
| TurnOverAction | 结束当前回合 |
| InitAction | 初始化模拟状态 |
| EmptyAction | 无操作/占位动作 |

每个动作同时可以有真实执行函数和模拟函数，并带 creator、recalculate 等属性。策略先通过 generate*Actions 或卡牌权重找到动作，再由执行器调用真实点击；MCTS 则只在 clone 的 War 上调用模拟函数。

CardAction 提供的真实执行 API 包括 power、attack、attackHero、pointTo、lClick、launch、trade、chooseOne、forge 等。默认动作通过 DefaultCardAction 和 commonActionFactory 兜底。

## 10. 卡牌识别、数据库与文本解析

### 10.1 卡牌数据库

DBConfig 和 CardDBUtil 使用 SQLite 查询 cards 表，按卡牌名称、CardID、DBF ID 查询卡牌信息。数据库路径会依次尝试当前目录、父目录、hs-script-app 目录和仓库根目录中的 hs_cards.db。

CardInfoData.indexCard 会把数据库卡牌文本送进描述解析器，并把生成的 CardInfo 放入全局 CARD_DATA_TRIE。应用层的 CardGroupUtil 会在启动时清空/重新应用启用的卡牌组，因此卡组配置可以覆盖或补充默认权重与动作。

### 10.2 CardDescriptionParser

解析器先清理 HTML、注释、空白和文本格式，再根据关键词做保守解析：

- 支持前缀：战吼、连击、选择一张、法术迸发等；
- 识别伤害、治疗、增加攻击/生命、冻结和目标域；
- 目标域区分友方/敌方、随从/英雄、单体/全体；
- 对死亡亡语、激励、奥秘、随机、召唤、变形、发现、被动触发等复杂或不可靠文本会拒绝自动生成动作；
- 对全体、随机分配和未支持语法返回 no-point 或不生成动作。

解析结果由 ByteBuddy 生成 CardAction 子类，并由 ParsedCardActionFactory 按 CardID 缓存 Supplier。解析器测试覆盖 Fireball、Consecration 等文本，另有拒绝条件和动作生成测试。

### 10.3 CardActionEnum 与目标选择

CardActionEnum 把目标范围抽象成：

POINT_MY_HERO、POINT_RIVAL_HERO、POINT_MY_MINION、POINT_RIVAL_MINION、POINT_MY、POINT_RIVAL、POINT_MINION、POINT_HERO、POINT_WHATEVER、NO_POINT。

playExec / powerExec 根据枚举选择目标，并在敌方目标中优先考虑斩杀或伤害最大化等规则。

## 11. 策略 SDK、执行器与内置策略

### 11.1 SDK 合约

DeckStrategy 是策略插件的抽象基类，必须实现：

~~~text
name()
getRunMode()
deckCode()
id()
executeChangeCard(HashSet<Card>)
executeOutCard()
executeDiscoverChooseCard(Card...): Int
~~~

可选能力包括：

- needSurrender：策略是否要求投降；
- referWeight、referPowerWeight、referChangeWeight、referCardInfo：应用层是否把对应数据装入策略环境；
- execChooseTimeLine：是否参与时间线保留/回溯选择；
- description、pluginId 和重置逻辑。

策略通过 ID 判断相等，应用会过滤空名称、空 ID 和不支持当前运行模式的策略。

### 11.2 DeckStrategyActuator

这是应用层把日志事件交给策略、再把策略结果交给鼠标的桥：

1. changeCard 等待换牌界面稳定，克隆当前手牌并排除硬币。
2. 调用 executeChangeCard，策略从集合中移除想换掉的牌。
3. 点击确认。
4. outCard 检查策略、我方玩家、对手玩家和回合有效性。
5. 调用 executeOutCard。
6. 在策略返回后取消当前指向/动作，必要时重复结束回合。
7. discoverChooseCard 对策略返回的下标做范围保护，异常时回退到第一张。
8. chooseTimeLine 根据策略结果点击保留或回溯。
9. checkSurrender 在策略请求投降时异步调用 GameUtil.surrender()。

### 11.3 内置基础策略

| 策略 | 运行模式 | 核心行为 |
|---|---|---|
| HsCommonDeckStrategy 基础策略 | 标准、狂野、休闲、练习 | 基于 CARD_DATA_TRIE 和 DeckStrategyUtil 使用技能、清场、普通出牌和星舰发射；换牌时默认留下费用不超过 2 的牌；发现默认返回索引 1 |
| HsRadicalDeckStrategy 激进策略 | 标准、狂野、休闲、练习 | 先激活地点；尝试计算手牌组合、硬币价值和出牌顺序，再回退到基础策略 |
| HsSurrenderDeckStrategy 秒投策略 | 标准、狂野、休闲 | reset 时把 needSurrender 设为 true，不主动出牌 |
| HsMCTSDeckStrategy MCTS 策略 | 标准、狂野、休闲、练习 | 使用 MCTSArg 分阶段搜索：前段较长思考和少量回合因子，后段缩短截止时间并提高回合因子 |
| HsOnlyFaceDeckStrategy 打脸策略 | 标准、狂野、休闲、练习 | 在 MCTS 评分中显著放大嘲讽和英雄生命影响，优先脸部压力；其他动作继承 MCTS |

默认策略 ID 为激进策略：e71234fa-1-radical-deck-97e9-1f4e126cd33b。

### 11.4 MCTS

MCTSDeckStrategy 的通用流程是：

~~~text
当前 War
  → 清除对手手牌中的未知信息
  → deepClone
  → MonteCarloTreeSearch
       → select：UCB/访问次数/胜率
       → expand：生成手牌、英雄技能、战场攻击和结束回合动作
       → simulate：在 clone 上执行模拟动作
       → backprop：回传终局分数
  → 取最优子节点
  → 执行动作序列
~~~

搜索默认有最大深度 10，支持截止时间、每回合因子、每回合搜索次数和多线程计算。WarScoreCalculatorBuilder 默认综合我方与对手的手牌、战场、牌库、奥秘、资源和卡牌权重；打脸策略在此基础上把英雄和嘲讽加入更强的权重。

## 12. 插件系统

### 12.1 Plugin 元数据

所有插件实现 hs-script-plugin-sdk 的 Plugin 接口，必须提供：

author、version、id、name、homeUrl。

可选提供：

description、graphicDescription、updateUrl、getInfoString、cardSDKVersion、strategySDKVersion、init。

类型分为：

- CardPlugin：提供 CardAction。
- StrategyPlugin：提供 DeckStrategy。

PluginWrapper 把一个 Plugin 与它发现到的 SPI 实例绑定，并暴露 JavaFX enabled 属性；插件开关变化时会触发动作/策略管理器重建。

### 12.2 ServiceLoader 注册

插件 JAR 必须在 META-INF/services/ 中注册实现类，例如：

~~~text
club.xiaojiawei.hsscriptcardsdk.CardPlugin
club.xiaojiawei.hsscriptcardsdk.CardAction
club.xiaojiawei.hsscriptstrategysdk.StrategyPlugin
club.xiaojiawei.hsscriptstrategysdk.DeckStrategy
~~~

应用通过 Java ServiceLoader 加载：

- 内置 classpath 插件；
- plugin/ 目录下的外部 JAR 或插件目录；
- ClassLoaderUtil 创建的外部类加载器。

外部插件中 Plugin 和 SPI 实例会绑定到同一插件包装器；应用会过滤内部 SPI 包、去重内部实例，并按 plugin ID 选择最高版本。

### 12.3 卡牌插件 Scope

CardPlugin.pluginScope() 默认是受保护范围；范围决定卡牌动作可以被哪些策略使用：

- PUBLIC：映射到公共 CARD_ACTION_MAP[""]。
- PROTECTED：默认只映射给同 plugin ID 的策略。
- 自定义 ID 列表：只映射到列出的策略插件。

内置基础卡牌插件使用 public scope，因此基础英雄技能和卡牌动作可以被默认策略直接使用。

### 12.4 版本与覆盖规则

PluginManager 大致按以下顺序处理：

1. 读取禁用的卡牌插件和策略插件 ID。
2. 构建所有 Plugin 与 SPI 的 wrapper。
3. 调用启用插件的 init()。
4. 按插件 ID 用 Release.compareVersion 选择最高版本。
5. 根据 Scope 把卡牌动作放入不同策略可见的 Map。
6. CardActionManager 为每个插件建立 LikeTrie<()->CardAction>，支持精确 CardID 和 % 通配 CardID。
7. DeckStrategyManager 建立可观察策略集合，持久化默认策略和工作时间规则覆盖。

因此开发插件时，id、version、SPI 资源文件和 CardID 通配范围都属于运行时契约，不能只看类名。

### 12.5 模板插件的最小流程

卡牌模板的步骤：

1. 修改 TemplatePlugin 的元数据。
2. 编写继承 CardAction.DefaultCardAction 的卡牌类。
3. 在 META-INF/services/...CardAction 注册完整类名。
4. 编译 mvn clean package。
5. 把生成的 JAR 放到主程序 plugin/ 目录。

策略模板的步骤类似：

1. 修改 TemplatePlugin。
2. 实现 TemplateStrategyDeck 的换牌、出牌、发现逻辑。
3. 在 META-INF/services/...StrategyPlugin 和 ...DeckStrategy 注册完整类名。
4. 编译后把 JAR 放到 plugin/。

## 13. 内置卡牌插件的实现方式

hs-script-base-card-plugin 的插件 ID 是 xjw-base-plugin，提供 public scope 的基础卡牌适配。

服务注册的英雄技能包括死亡骑士、恶魔猎手、德鲁伊、猎人、法师、圣骑士、牧师、萨满、术士和战士；还注册了硬币和一批战士卡牌，例如：

AcolyteOfPain、Bash、Bladestorm、Brawl、CargoGuard、Execute、FieryWarAxe、HeavyPlate、PlatedBeetle、ShieldBlock、ShieldSlam、Slam、TarCreeper、Whirlwind、SanguineDepths、DeathwingMadAspect。

实现习惯是：

- ClickPower 把英雄技能映射到 execLClick。
- PointPower 负责需要目标的英雄技能。
- 卡牌类重写 execPlay、execPower、回合开始/结束、受伤、亡语或战吼回调。
- TarCreeper 等效果通过回合生命周期回调修改状态。
- AcolyteOfPain、CargoGuard、PlatedBeetle 等展示了受伤、回合结束和亡语模型的用法。

这部分代码是理解新卡动作的最好参考，比模板更接近真实执行边界。

## 14. 外部 WeightHandlerStrategy 策略

这是一个独立的用户策略插件，不属于根 Maven 模块，但源码已经直接纳入当前仓库。插件入口：

- Plugin：lin.WeightHandlerPlugin，策略 SDK 版本声明为 4.9.0-GA。
- Strategy：lin.WeightHandlerStrategy，运行于标准、狂野、休闲、练习。
- Strategy ID：e71234fa-1-weightHandler-deck-97e9-1f4e126cd33b。

### 14.1 主要运行流程

~~~text
WeightHandlerStrategy
  → ComboDomain(WAR)
      → 建立 JarClassLoader
      → 启动 Koin(DBModules + ParseCardWeightInfoModule)
      → MyWarManage
          → 读取 CardWeightInfo SPI
          → 把 Card 转成 ComboCard
          → 解析 combo/group/card 配置
      → WeightHandlerDomain.findCombination
      → 执行最优组合
      → 战场变化后重新加载并递归找下一组
~~~

策略支持按权重换牌、组合出牌、攻击、发现和生命周期处理。MyWarManage.executeEnvironment 会先重载手牌/战场信息，再处理亡语、地点和清场，最后执行组合策略。

### 14.2 数据和扩展点

默认数据库路径是运行目录下的 weightHandlerStrategy.db，通过 Spring JDBC + SQLite 访问：

- combo_info：组合卡与 comboWeight；
- weight_group：权重组及条件；
- 卡牌权重信息：由 CardWeightInfoProvide 和解析器转换。

comboWeight 在现有实现中同时承担多个语义：换牌时表示正负取舍、出牌时表示顺序、组合时表示一起出牌的权重。这是维护时最需要先确认的隐式协议。

Java SPI 扩展点如下：

| SPI | 用途 |
|---|---|
| WeightCondition | 按战场、种族、手牌、墓地等条件修正权重 |
| CardWeightInfoProvide | 提供卡牌的默认权重信息 |
| ParseCardWeightInfo | 把配置/代码信息转成运行时权重 |
| CardRule | 单卡特殊规则 |
| WeightHandler | 组合或单卡的权重处理器 |
| LifecycleRegister / RoundLifecycle | 规则启动、每局和回合生命周期 |

源码中还包含 WeightConditionEngine：它尝试从脚本目录加载 *.cardstrategy.kts，使用 Kotlin Script Engine 和文件监听热重载，但真正的 calculateCardWeights 仍是 TODO，因此不能把它当成已经完成的主路径。

README 已明确记录的局限包括：发现和地点事件处理不完整、卡牌权重与组合模型耦合、缺少 UI 导致数据库/代码配置容易填错、同一个 ComboCard 模型承载过多状态。

## 15. UI、设置与持久化

### 15.1 JavaFX 页面

WindowEnum 定义了主窗口、启动页、设置、插件设置、策略设置、卡组设置、开发者设置、工作时间、统计、游戏分析、游戏测量和游戏覆盖层等页面；FXML 位于 hs-script-app/src/main/resources/fxml/。

- 编辑卡组信息组；

配置分组包括：init、plugin、other、time、strategy、mouse、window、behavior、system、version、dev、weight、layout。

| 工作时间 | WORK_TIME_RULE_SET、WORK_TIME_SETTING、WORK_TIME_RULE_HIGH_PRIORITY |

### 15.3 卡牌组与统计

CardGroupUtil 使用 Jackson 读写 data/cardgroup/*.cardgroup，提供创建、保存、删除、重命名、导入、导出和启用应用。启动时 applyEnabledCardGroups() 清空全局 CARD_DATA_TRIE 并按启用组重新建立卡牌信息。

WarEx 是应用层对 SDK WAR 的包装：

- startWar 重建玩家/区域，设置开始时间、当前运行模式和 inWar；
- endWar 计算胜负、经验、连胜、悬挂时间等；
- StatisticsListener 在战局数变化后写入统计数据库；
- 战局结束会清理 ParsedCardActionFactory，避免跨局复用旧的解析动作。

## 16. Windows 原生能力与坐标自动化

### 16.1 鼠标控制模式

MouseControlModeEnum 至少覆盖消息、事件和驱动等路径：

- 消息模式：向窗口发送点击/文本等消息，通常不需要物理移动鼠标。
- 事件模式：模拟 Windows 输入事件。
- 驱动模式：通过 Interception 驱动实现更底层的鼠标输入，安装/加载/释放由 DriverInitializer 和 CSystemDll 管理。

ConfigExUtil.storeMouseControlMode 在模式切换时负责安装或释放驱动，驱动模式还会受到管理员权限、Windows 驱动安装和安全软件影响。

### 16.2 游戏窗口坐标

GameUtil 把游戏窗口归一化为 GameRect，集中保存中心、确认、结束回合、英雄、英雄技能、手牌、战场、发现、选择一张、时间线、星舰发射等矩形。

这种设计让策略调用 GameUtil.getMyHandCardRect() 等高层方法，而不是在策略里写屏幕像素；但矩形仍是针对游戏 UI 布局的经验参数，分辨率、缩放、窗口比例或多显示器变化会影响可靠性。

### 16.3 进程与注入

CSystemDll / SystemUtil 提供查找窗口、查找进程、启动/终止战网和炉石、窗口置前、移动/缩放窗口、目录保护、系统托盘和 hook 控制。InjectGameStarter 根据开发者配置选择注入内容；ScriptStatus 会缓存并验证游戏/战网窗口句柄，失效时重新寻找。

## 17. 更新器与版本服务器

### 17.1 tools/hs-script-update

这是独立 Go 程序，命令行入口支持：

~~~text
update <zipPath> <targetDir> [--pause] [--pid=<pid>] [--main-program=<path>] [--nogui]
check <version> [-d] [-n] [-i] [-r gitee|github]
latest [-d] [-n] [-i] [-r gitee|github]
~~~

更新流程：

1. 等待主程序退出，最多约 5 秒，超时会强制结束进程。
2. 检查更新包和目标目录。
3. 在目标目录创建 _temp_update，解压 ZIP，并防止 Zip Slip 路径穿越。
4. 通过目标目录 lib/ 是否有 JAR 判断 JVM/Native。
5. JVM 版保留 config、data，只更新基础卡牌插件和基础策略插件目录。
6. Native 版保留 config、data，覆盖其余文件。
7. 清理临时目录；若更新包位于目标目录则删除更新包。
8. 可自动启动主程序。
9. 尝试把新 update.exe 复制到 .bak，由退出后的 cmd 命令完成自替换。

版本仓库支持 Gitee 和 GitHub。版本比较提取数字段，并按 GA > PATCH > DEV > BETA > TEST 处理同数字版本的后缀。

### 17.2 tools/hs-card-update-util

这是一个独立的 Go 数据导入工具，入口是 `main.go`，默认从 `https://api.hearthstonejson.com/v1/latest/zhCN/cards.json` 获取卡牌 JSON，默认写入当前目录的 `hs_cards.db`。命令行参数采用 `--key=value` 形式：

~~~text
--remoteURL=<cards.json 地址>
--dbPath=<SQLite 文件路径>
--proxyAddress=<host:port，可选>
~~~

运行链路是：

1. 解析远端地址、数据库路径和代理参数。
2. 通过 `net.GetJsonIO` 创建 HTTP 客户端；没有显式代理时使用环境代理。
3. 创建 `cards` 表，字段覆盖卡牌 ID、名称、职业、费用、身材、文本、类型、机制、种族等。
4. 使用 `json.Decoder` 流式读取数组，避免先把完整 cards.json 加载进内存。
5. 将 `mechanics`、`races` 数组拼成逗号分隔字符串，通过 `INSERT OR REPLACE` 按 `cardId` 写入 SQLite。
6. 用独立 goroutine 刷新命令行转圈进度，并在完成后停止。

它是卡牌数据链路的生产端，`hs-script-card-sdk` 中的 `CardDBUtil` 是消费端；后者按 `name`、`cardId`、`dbfId` 查询同一张 `cards` 表，再交给卡牌解析和动作生成流程。

### 17.3 tools/hs-script-version-server

版本服务器使用文件系统作为存储，默认监听 8080，提供：

| 方法 | 路径 | 行为 |
|---|---|---|
| GET | /repos/{user}/{project}/releases/latest | 返回最新正式版本 |
| GET | /repos/{user}/{project}/releases | 返回按发布时间倒序的全部版本 |
| GET | /{user}/{project}/releases/download/{tag}/{filename} | 从 releases 目录直接发送文件 |
| GET | /health | 返回 OK |
| GET | /static/* | 暴露 releases 目录静态文件 |

如果 releases/releases.json 存在则优先读取；不存在时扫描 hs-script_*.zip，从文件名提取版本，并把 -DEV、-BETA、-TEST 标为预发布。这里要注意：扫描回退逻辑只匹配 hs-script_，Native 文件名是否能被自动扫描不能仅凭该回退逻辑保证，应使用显式 releases.json 或核对服务器版本。

## 19. 已确认的边界、风险与维护建议

### 19.1 运行边界

- 这是 Windows 优先的应用：JNA、Windows API、注册表、Battle.net 窗口、驱动和多个 DLL 都是运行时依赖。
- 需要正确的程序运行目录；换工作目录可能导致配置、数据库、插件和资源找不到。
- 运行前通常需要管理员权限，尤其是驱动、注入、目录保护和部分窗口控制能力。
- Native 版本与 JVM 版本在插件能力、反射、ServiceLoader 和资源配置上并不等价。

### 19.2 并发边界

项目同时使用 JavaFX 属性、ScheduledExecutor、固定线程池、虚拟线程、锁和多个后台线程。暂停和重启会取消任务，但日志监听、发现、MCTS、UI 和 native 回调之间仍存在异步交叉，因此修改全局 WAR、Mode、PauseStatus 时必须考虑线程安全和可见性。

重点线程池来自 hs-script-base：

| 线程池 | 用途 | 默认规模 |
|---|---|---|
| LAUNCH_PROGRAM_THREAD_POOL | 启动程序 | Scheduled，2 |
| LISTEN_LOG_THREAD_POOL | 日志轮询 | Scheduled，4 |
| EXTRA_THREAD_POOL | 辅助任务 | Scheduled，10 |
| CORE_THREAD_POOL | 启动核心链 | 固定 2，队列 1 |
| CALC_THREAD_POOL | MCTS/计算 | CPU 核心数至 2 倍，队列 8 |
| VIRTUAL_THREAD_POOL | 阻塞型短任务 | 虚拟线程 |

### 19.3 解析和策略边界

- Power.log 的字段解析是对游戏日志格式的定制解析，版本更新后需要优先检查实体字段、标签和区块格式。
- 卡牌文本解析器只对已覆盖的自然语言模式生成动作；复杂随机、发现、召唤、被动和多段效果需要手写卡牌动作。
- MCTS 使用未知信息清理、随机占位和评分函数，得到的是模型内最优，不等于真实游戏的完全信息最优。
- DeckStrategyUtil 和基础策略中存在很多依赖当前 UI/卡牌模型的启发式权重，扩展新卡时应优先写独立 CardAction，再决定是否修改通用策略。
- WeightHandlerStrategy 的组合模型和权重语义耦合较重，修改数据库表或 SPI 时必须同步检查换牌、出牌、攻击、发现和生命周期路径。

### 19.4 已知源码缺口

- hs-card-update-util 没有检查 HTTP 状态码，也没有事务包裹整批 upsert；远端返回错误页面或中途退出时，应先备份数据库并检查导入结果。
- hs-card-update-util 使用 `INSERT OR REPLACE`，SQLite 可能删除旧行后重新插入，依赖自增 `id` 的外部代码不应把该字段当稳定标识。
- hs-card-update-util 的进度显示变量没有同步保护，主要适合命令行单进程导入，不应当作可复用的并发库。
- 外部权重插件的 Kotlin Script calculateCardWeights 仍为 TODO，不是当前权重主路径的完成实现。
- 外部权重插件的 `AbsDefCondition`、`ComboConditionByRace` 仍包含未实现分支；模板策略中的换牌、出牌、发现方法也保留了待填写的示例骨架。
- Native 版本的插件兼容、资源反射和 ServiceLoader 行为需要在真实 Native 构建上单独验证。
- 版本服务器的目录扫描回退只识别 JVM 命名格式，Native 发布建议显式维护 releases.json。

### 19.5 本轮源码内联复核

- 转换前已确认 13 个子模块的 HEAD 与根仓库原 gitlink 一致，且各自工作树均为 clean，因此导入内容具有明确提交来源。
- `tools/hs-card-update-util` 的导入基线是 `c70398d5c93887dd937fa0b6f33f6dce2aebd0b9`；它已纳入卡牌数据库更新链路的阅读范围。
- 转换后 `.gitmodules` 和目录内嵌套 `.git` 均已移除，所有模块、工具和外部策略都作为当前仓库的普通源码维护。
- 文档中的依赖图、启动链、日志解析、WAR 状态机、策略执行器、SPI 插件和更新流程均以导入后的实际源码再次核对。

## 22. 总结

项目的最重要设计是“日志驱动状态机 + 可模拟的战斗模型 + 可插拔的动作/策略”：

1. hs-script-app 管理 Windows 生命周期、UI、路径、日志和状态。
2. hs-script-card-sdk 把 Power.log 还原成可计算的 War、Player、Card 和 Action。
3. hs-script-strategy-sdk 抽象换牌、出牌、发现、时间线和投降。
4. hs-script-plugin-sdk 用 Java SPI 和 Plugin wrapper 把卡牌实现、策略实现与客户端解耦。
5. 内置基础插件提供可运行的默认能力，模板提供扩展入口，外部权重插件展示复杂策略的另一种实现。
6. Go 更新器和版本服务器构成独立发布链路，配置和数据目录在更新时被有意保留。

后续维护最值得优先保护的契约是：Power.log 格式、WAR 实体/区域更新、SPI 文件名、插件 ID/版本、策略动作的模拟/真实执行一致性，以及 Native/JVM 两种运行模式的资源差异。
